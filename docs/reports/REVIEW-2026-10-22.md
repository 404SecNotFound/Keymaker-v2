# Keymaker review, 2026-10-22

**Date** 2026-10-22. **Tree** `main` at `dd5b350`. **Kind** a self-review, not an external audit.

**Method.** Ten finders each read one dimension of the project read-only (crypto core, the React state hook, product and UX, tests and CI, code health, documentation and the heir path, performance, residual security, accessibility, and the Python reference) and reported findings with the evidence behind them. Every P1 finding then went to three verifiers with different briefs (refute it, reproduce it, and judge whether it is worth fixing), and every P2 finding to one verifier briefed to refute it. A finding is kept only on a majority. P3 findings were not independently verified and each is labelled [Unverified]. Five strategists proposed next moves from five angles (adoption, assurance, engineering, ecosystem, and a contrarian cut), and three judges scored all thirty-eight proposals on impact, feasibility and effect on the trust claims. Every path and line number cited below was checked against `main` before this report was committed. The six paths that do not exist yet are files this report proposes to create, and each says so.

---

At dd5b350 the project is in a strong position. Every roadmap phase except the owner-only items is shipped, three self-review security passes have landed, the parity suites pass on this tree (keym2.py selftest 695, crosstest2 553, recovery_test 194, `test:keymaker` 315), and the ten finders found nothing P0 anywhere. Sixty-one findings reached the verifiers. Forty-three were kept and eighteen refuted; after merging the three duplicate pairs (audio carrier, hash-wasm, keym2.py FIFO race) and the two overlapping SECURITY-AUDIT.md items, thirty-nine distinct items remain, and seventeen of them were settled a level below what the finder filed. A further forty-four P3 items carry only their finder's confirmation and are listed as unverified. The judges scored thirty-eight proposals for the plan; the top three were "Fix the broken disclosure path, then make it a release gate" (13.67), "the live site serves the release bytes, not main" (13.33) and "delete the architecture prose that drifted" (13.0). The one thing to fix first is the audio carrier. The app writes a WAV that nothing outside the app can open, the README and the kit dialog say the independent decryptor still applies, and three verifiers reproduced an heir being told "decryption failed" on a WAV that holds a perfectly good backup. That is the only finding in this report that can leave someone without their backup.

## 6. What not to do

- **No fourth self-review pass before an outside account files an issue.** Pass three found nothing above Medium, and the next finding the project cannot generate for itself has to come from a second mind.
- **Do not post before E1 to E5 and Bet 1 land.** A post cannot be corrected by a later commit, and today it would send a sceptic to a disabled report button, a false audio claim and a stale design document.
- **Do not make PBKDF2 the default for typed passwords.** Bet 2 is safe only because a 90-bit generated passphrase makes memory hardness irrelevant, and a typed password has no such floor (KM-06).
- **Do not write a Go port, a stdlib AES-GCM or any third implementation yourself.** Its value is independence, and the same author writing it adds a parity burden without adding independence.
- **Do not split `reference/keym2.py` or move its selftest out.** The recovery kit and `docs/RECOVERY.md` depend on one file that checks itself offline.
- **Do not relicense or publish an npm package now.** It is a public API promise on a security library with no consumer asking, and the licence question is unresolved.
- **Do not rebuild the test infrastructure (registry, persistent bridge, token generator).** A refactor of the gates is where a negative control stops biting unnoticed, and none of these removes a user-facing defect.
- **Do not redesign the palette again before there are users to see it.** Three palettes in ten weeks at zero stars is maintainer time taken from thesis work.
- **Do not narrow §4.7's "cannot be opened offline" sentence on vendor documentation.** No physical authenticator has ever been tested (`docs/AUDIT-BRIEF.md`), and RECOVERY.md's plain answer is worth more to an heir than a conditional.
- **Do not take Firefox and WebKit off the PR gate before sharding is tried.** Sharding gets the same wall-clock win without letting an engine-specific regression reach main first.
- **Do not commission an audit for publicity** (Cut table). It selects the wrong auditor, and an audit for findings is the version worth paying for.
- **Do not ship a video walkthrough or README clip** (Cut table). It cannot be executed against the code and goes stale silently.
- **Do not ship plausible deniability or a duress password** (Cut table). The feature's existence in an open-source tool is itself the evidence it was meant to hide.
- **Do not add PAKE or croc-style transfer** (Cut table). It needs a rendezvous server, and the zero-server property is the product.
- **Do not add KEYM-in-PNG steganography, or let the audio carrier claim hiding** (Cut table). Obscurity is not security, and the carrier is kept only as a transport.
- **Do not add a TOTP vault, an OPFS workspace or importers** (Cut table). Each one dilutes focus or puts plaintext-adjacent state into durable storage.
- **Do not add Reed-Solomon parity** (Cut table). AEAD already rejects corruption, and an outer layer needs its own spec and parity for a complaint nobody has made.
- **Do not add a post-quantum hybrid or encrypt-to-recipient** (Cut table). It is a different, keypair-based product until WebCrypto ships ML-KEM.
- **Do not add wipe-on-N-attempts, self-destruct, time-lock or breach checks** (Cut table). They are impossible without a server, and documenting them as impossible is the feature.
- **Do not auto-copy a generated password to the clipboard** (Cut table). The clipboard is readable by other applications and sometimes synced.
- **Do not call passkeys "hardware-grade", and do not soften "shares are password-equivalent"** (Honest framing). The passphrase fallback bounds the passkey slot, and any k shares decrypt without the password.

## 7. Open decisions for the owner

**Will you switch on private vulnerability reporting today, and is there any bounty?** The switch is one click and makes `SECURITY.md:7-9` true. A money bounty needs a budget and a scope (format and slot walk, P0 and P1 only), and the judges said credit and a CHANGELOG line are enough without one.

**Do you accept that the site moves only when you tag (Bet 1)?** The served bytes become the attested release, and the trust anchor stops changing with every dependabot merge. The cost is that every hot fix needs a tag, so the release cadence becomes your job rather than CI's.

**Custom domain and a header-capable host, before the first post or never?** A real CSP header closes the worker-fetch gap and the framing gap, and a custom domain ends the shared-`github.io` cache-poisoning risk recorded in PR #267. It adds a registrar and a host to the trust chain, and every printed URL must redirect for as long as paper kits exist.

**Will you fund, or apply for a grant for, an external design review of the format?** It is the only item that can find a wrong idea shared by the spec, both implementations and every test, and the seven questions are already written. [Unverified] A boutique engagement for the format alone is likely low five figures USD, and the questions and pinned commit should be published before the engagement so the scope cannot look chosen afterwards.

**Should a generated passphrase default to PBKDF2 (Bet 2), or should the page profile stay opt-in?** The default puts every inheritance backup in reach of the one reader that needs no toolchain. Some reviewers will read it as a KM-06 regression unless the provenance condition is stated everywhere the KDF is named.

**Keep or freeze the audio carrier's writer once the Python reader lands?** With E3 the carrier honours the Cut table's condition, and nothing already made becomes unreadable either way. Freezing the writer removes 1,063 source lines and a browser decode path for arbitrary MP3, FLAC and Ogg in a security tool, but it deletes a README "yes" cell nobody else offers.

**Should share recovery try other k-subsets when the lowest-index set fails?** PR #267 left this open. A forged low-index strip poisons a set that still holds k genuine ones, and the security-residual finders measured a leave-one-out search at 18 ms and the full C(16,8) search at about 16 s. The fix rescues real heirs, but a search loop changes how the error appears and must be written into §4.6 before either implementation changes.

**Should the recovery kit's `requirements.txt` carry hashes?** CI installs with `--require-hashes` from a different file, so the kit's pip path is not what CI tests, and it pins only 2 of 6 packages. Hashes make the kit's install exactly what was tested, but they fail on any platform whose wheel hash is not listed, which is the heir's machine in 2040.

**When and where do the posts go, and in what order?** The judges favour r/crypto first because it asks for format review, then r/privacy and Show HN, then the seed-phrase community the first door is built around. Leading with Bitcoin gives the posts a concrete story but can narrow the brand, and the deliberately generic seed-mode wording must not change to suit it.

**Should the palette, icon and screenshot gates stop blocking merges?** No trust claim rests on a colour, and a weekly report frees a browser install per PR and maintainer time per surface. The gates do catch contrast failures users feel, so this is a sequencing call on your design investment, not a judgement of it.

**Crypto core.** The core and the three format readers are in good shape on every axis probed. NFC normalisation is applied identically in the v2 reader, the v1 reader, the self-extracting page and both Python references; the IGNORABLE sets are byte-identical (verified by dumping code points from both sources); every lazy-import promise forgets its rejection; version dispatch on short or ambiguous input is total and reaches no KDF; and v3/v4 chunk layout and Padmé padding round-trip at 0, 1 MiB, 1 MiB+1 and 2 MiB (run). Nothing P0 or P1. What remains are spec-silent reader divergences the byte-parity gate cannot see (a password over 1,024 UTF-16 units, an identical strip pasted twice), two error paths where a resource or ceremony failure is reported as a wrong secret or not at all, and two caching and calibration decisions that silently weaken a written container after a transient failure.

**Tests and CI.** The suite is large and mostly honest. 363 Playwright tests per engine (about 40 runtime-skipped on Firefox and 50 on WebKit by engine gates), 43 Node and Python suites all wired into a workflow with `test:readme` gating the README list, the fixture corpus asserted in both languages, the base-path layout built and served in browser.yml, and the no-worker fallback exercised on all three engines. Flakes are rare now (one flaky test in 14 sampled green runs; the two CLAUDE.md flakes were de-timed in 3007d5c). The two real problems are new. The third-pass FIFO selftest has a thread race that already turned conformance red on an unrelated pip bump, and the pending dependabot npm PR fails all ten axe views because axe-core 4.14 enables a rule the command-bar button violates. The PR gate is WebKit at about 14 minutes; sharding WebKit and Firefox and path-gating the 4.3 minutes of fuzzing would roughly halve it.

**Accessibility.** Better than most projects this size. Every dark-theme text pair clears AA (31 pairs computed from globals.css, lowest 4.60:1), reduced motion is a global rule with both halves tested, every icon-only button has a name, the seed grid and command bar are correctly wired combobox and listbox patterns, and the Shamir and camera dialogs are Radix-trapped with sensible escape rules. axe in CI covers names, labels, text contrast and ARIA validity; it cannot see focus visibility, where focus lands after a control removes itself, touch-only dead ends, non-text contrast or live-region timing, and that is exactly where the defects are. The one serious finding is that no text field has a visible keyboard focus indicator. Secondary, the self-dismissing buttons drop focus to body, the self-extracting page's success is silent to a screen reader, seven tooltips cannot be opened by touch, and the axe and touch-target sweeps never reach the Recovery tab, the Audio tool, any open dialog, the verify page, the self-extracting page or the printed vault.

**UX and product.** The product is in unusually good shape for its size. Copy is honest, steps never run ahead of evidence, every error provoked was named, and the paper vault's printed procedure works end to end today (confirmed by running join, inspect and decrypt --share against keym2.py). The gaps sit at seams the walkthrough does not cross. The docs name a confirm step that the form does not have, a file-mode backup exists only as one auto-triggered download with no way to re-download, and file-shaped inheritances fall off the plan. Mobile has never been opened on a device. The rest is stale copy that predates v4 and the QR strips, plus two small CLI message bugs.

**Code health.** Architecture is sound where it matters. The crypto core is a lazy-loaded leaf, the worker boundary is typed with `satisfies` against one request union, strict TypeScript passes with 0 errors and one real `any`, every package.json dependency is used, 56 of 59 browser specs share one helpers file, and pure logic already has an extraction pattern (33 node suites import src/lib). The debt is concentrated and measurable. 6,413 lines of parity-gate scripts that tsc never sees (22 real type errors hidden, one in the dispatch gate itself), hash-wasm shipped whole because of a namespace dynamic import, format constants restated across keymaker-crypto, shared and selfextract, one 3,610-line hook and one 1,889-line component with no node-level tests, 24 copies of the esbuild bridge, and no linter. The plan is incremental. Typecheck the scripts first, then the argon2-only entry, then the shared bundle helper, the request-builder extraction, the JSX split, unused-locals flags and dead-export deletion.

**Python reference.** The core is in excellent shape. keym2.py selftest (695 checks, 3.1 s), keym.py selftest, crosstest.py, crosstest2.py (553 checks, byte equality for v2/v3/v4 including the published v4 §8 vector, paper parts, self-extracting pages, passkey PRF, Shamir) and recovery_test.py (194 checks executing RECOVERY.md and WALKTHROUGH.md) all pass on this tree, the conformance pins agree with requirements.txt, and keym2.py parses as Python 3.10. The gaps are at the edges an heir meets, not in the format code. The audio carrier has no Python reader, no conformance and no mention in RECOVERY.md despite the spec's claim that the decryptor "applies unchanged"; the CLI layer let a wrong share-material warning ship on every add-shares; nothing runs on Windows or macOS and the heir docs have no Windows line; and the kit does not say how to check that a copy of keym2.py is genuine even though the signed release manifest already covers it.

**Docs and heir.** The executed documentation is accurate at dd5b350. recovery_test.py passes 194/194, `test:readme` passes, every CLI flag and sample output in RECOVERY.md matches keym2.py, and the stated KDF floors match KDF_LIMITS. The drift is all in prose nothing executes. The README's local-serve recipe cannot work against the tarball release.yml builds, the README promises keym2.py still applies to the audio carrier, HOW-IT-WORKS.md describes the frozen v1 format as the current pipeline with no banner, VERIFYING.md sends a distrustful reader to the wrong script, and SECURITY-AUDIT.md, AUDIT-BRIEF.md and the changelog do not record the two October passes. From the heir's side the kit is complete for .keym, `keym2:` text, paper and shares but has no one-page card and no Windows variant. One non-doc defect was confirmed in passing, the race in keym2.py's pipe self-test.

**Performance.** Measured, not reasoned, wherever node could reach it. The off-thread design is sound and the calibration module is in good shape (64 MiB t=3 p=4 is 363 ms here, roughly 1-2 s on a mid-range phone). Three things cost real users. An armored text file of a few tens of MB freezes the tab for seconds and can crash it near the cap, 185 KB of dead hash-wasm blobs ship twice because a namespace import defeats tree-shaking, and the 100 MB path peaks at 4-5x the plaintext in the worker because the encrypt side still takes a redundant slice and both sides materialise a parts array plus a concat plus a pad copy. The three biggest wins are a split of the single 457 KB app chunk with a byte budget gate, the argon2-only entry (worker 278 KB to about 90 KB), and pre-sized chunk outputs to bring the 100 MB peak to about 2x.

**Security residual.** No P0 or P1 survived verification. The supply-chain and CI posture is better than most audited projects. Every external action is SHA-pinned, no pull_request_target, no secrets, per-job least privilege, the OIDC-holding sign jobs install with --ignore-scripts and are gated on manifests reproduced by independent runners, a tag-protection ruleset is active, and scripts/release-gate-test.mjs makes the gate executable (ran it, green). What an outside auditor would still flag is almost entirely in the trust documents and in what three self-review passes structurally cannot see. SECURITY-AUDIT.md's scope, baseline and CI table are stale by an order of magnitude and the October passes are not recorded; the passkey slot inherits the whole GitHub Pages origin as its RP ID and no document says so; the forged low-index share behaviour is by design but lives only in a PR body; and the slot walk is prose. Real authenticators, timing measurement of the GF arithmetic and heap-residue checks are what only an independent review with hardware would add.

**State hook.** The core discipline is sound. Every async path takes an opSeq token and re-checks it after each await, the lock interval, visibility and pagehide handlers are gated on isLoadingRef so a timer cannot interleave with a running job, and a node repro of crypto-client.ts with a fake Worker confirmed Stop mid-op, Stop mid-probe, sticky worker-error and no-worker Stop all behave as the comments claim. The real defects sit at the seams where one handler composes another without re-establishing the invariants the first one owns. returnToBackupTest re-opens the hidden-passkey bug the shares toggle was fixed for, the File and Text pills have no same-type guard, DOMExceptions and dearmorKeym2's plain Error are reported as a wrong password, and the async paper-part branch of a controlled textarea breaks typing. The structural lever is a pure operation-lifecycle reducer in the style of backup-workflow.ts, so the races that today need Playwright plus a ten-pass Argon2id to open a window can be pinned in node.
